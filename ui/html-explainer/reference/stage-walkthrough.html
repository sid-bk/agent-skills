Fulfilment priority engine, architecture v1

One engine run, from ruleset version to ranked pick list

The rules are data and the engine is code. A versioned ruleset says what to check and how much it counts; a pure evaluate() turns each open order's records into findings, a score, a band and a pick action. This page follows one nightly batch run through the code.

01

A ruleset version becomes effective

Before any run, load-ruleset reads a ruleset folder, validates it, runs its whole-order golden cases and stores it as an immutable version. Only a version whose golden cases all pass becomes effective.

EU retail (eu_retail) and US wholesale (us_wholesale) have the same file set. EU retail's rules.yaml is EU-RETAIL version 1.4.2.

Details: load-ruleset and immutable versions

Usage

python -m svc.cli.load_ruleset rulesets/eu_retail
python -m svc.cli.load_ruleset rulesets/eu_retail --effective-from 2026-11-03 --approved-by "Ops review" --note "..."

--effective-from defaults to today; --approved-by and --note are optional. A path is taken as given, or relative to the repo root.

What load() does (svc/cli/load_ruleset.py:38)

  1. Validate and hash. load_ruleset(ruleset_dir) (engine/ruleset.py) checks the ruleset and computes its SHA-256.
  2. Run golden cases. run_golden runs <ruleset>/golden/*.yaml against the ruleset's config, on the stub engine.
  3. Store the version with store_version (ruleset_store.py:174), in one database session.
    • An open draft for the ruleset blocks the load.
    • The same version label with the same content returns the stored version unchanged; with different content it is refused.
    • Rows go in while the version is a draft. Then the golden summary decides: all passed, the version becomes effective and records who approved it and when; otherwise it is stored, not effective, with the failing cases.
  4. Audit. A new version gets a config.version_loaded audit row with its SHA-256 and whether it is effective.
  5. Commit everything in one transaction.

It prints one line for the version and a pass or FAIL line per golden case. Exit code 0 only if the version is effective; a refusal, a missing folder or a not-effective version all exit 1.

What "immutable version" means

  • A stored version is never edited. Loading a known label with different content fails with "published versions cannot be edited, give the change a new version". A change always means a new version label, with its own hash, golden result and approval.
  • Every read is checked. read_version rebuilds the ruleset from its rows, re-hashes it, and refuses to run if the hash differs from the stored one (ruleset_store.py:291). Because content cannot change, load_config caches the frozen Config by version ID and hash.
  • Every run points at one. Each engine.run row records the config version ID and its SHA-256, so any finding traces back to the exact numbers that produced it.

Why it is built this way

  • A priority has to be reproducible and explainable later: "this order was Rush under EU-RETAIL 1.4.2" only means something if 1.4.2 cannot change afterwards.
  • Every business number lives in the ruleset, so editing a version in place would change warehouse behaviour with no review and no record of who approved it.
  • Effective dates choose between stable versions: a run picks the newest effective version whose effective date is on or before the run date.
  • The hash check catches the common slip of editing the YAML and reloading without bumping the version.

Things to know

  • It writes to the database, so treat running it as a change that needs sign-off, not a read.
  • A ruleset with no golden cases can never become effective: the summary needs at least one result, all passing.

02

A run starts

The runner picks the open orders for the ruleset's warehouses, resolves the version in effect on the run date, and reads every order's core.* rows. It is the only part that touches the database.

Details: execute_run

What execute_run() does (svc/engine/runner.py:361)

  1. Pick the orders. Batch mode: every open order routed to a warehouse of this ruleset, optionally only some warehouses. Single mode: the order IDs given.
  2. Resolve the version. effective_version takes the newest effective version with an effective date on or before the run date; none raises NoEffectiveVersionError. load_config rebuilds and hash-checks it.
  3. Open the run record. An engine.run row with the config version ID and SHA-256, engine implementation, mode, run date, a snapshot of every rule's ID, version and status, who triggered it, and the job ID.
  4. Evaluate with evaluate_orders (runner.py:312):
    • reads every order's rows in the warehouse's time zone;
    • adds the hard-stop event keys already raised on earlier run dates, so a hard stop is raised once;
    • builds each snapshot (a missing config key fails the run; any other error fails only that order);
    • if AN-P04 runs, attaches a peer table built from the batch's own orders;
    • calls the engine chosen by ENGINE_IMPL.
  5. Write the results (stage 09) and set the status: succeeded, partial (some orders errored) or failed (nothing scored). Commit.

Other pieces

  • evaluate_orders writes nothing, so the admin impact preview uses it as a dry run.
  • On a config or engine failure, fail() records the run as failed, with its errors, before raising RunFailedError.

Why it is built this way

Keeping all database work here is what lets the engine itself stay pure: the same snapshots, config and date always give the same result, which golden cases and the preview rely on.

Reads

Ruleset ID, run date, optional order or warehouse filter; effective_version and load_config from the ruleset store.

03

One frozen snapshot per order

build_snapshot(rows, cfg, as_of) applies the valid-line rules once, so every rule sees the same facts. It also works out the account tier and the active holds.

Pure and deterministic: the same rows and date always give the same snapshot.

Details: build_snapshot

What build_snapshot() does (svc/engine/snapshot.py:512)

  1. Takes plain row sections keyed by dictionary ID: order lines, payments, shipments, carrier events, stock levels, support tickets, returns and flags. Every row carries arrived_at, when it first reached the store.
  2. Applies the valid-line rules once: drops rows dated or arriving after as_of, cancelled, or with an unparsed SKU; converts weights to canonical units; drops impossible quantities; keeps extreme-but-possible quantities flagged verify-now. Each rejected row becomes a data-quality item.
  3. Sets the account tier. Tier B when any account-history collection exists (past orders, tickets, returns); guest checkout data only gives Tier A (config tier.b_when_any_of).
  4. Collects holds with an expiry and a scope: HOLD-01 customer-requested delay, split shipment pending, pre-order. Task-only holds (address unconfirmed) pass straight through to the priority.
  5. Returns a frozen OrderSnapshot, which also carries the hard-stop keys raised earlier and any injected findings.

Things to know

  • Holds never touch hard stops or floors (config never_kinds: [hard_stop, floor]).
  • An unknown row source raises ConfigKeyError, which fails the whole run, not just the order.

Why it is built this way

If every rule checked validity for itself, two rules could disagree about the same order line. Doing it once means every rule, the anomaly checks and the hard-stop path see exactly the same facts.

Reads

One order's raw rows keyed by dictionary ID, plus valid.*, units.*, tier.* and holds.* from config.

  • Impossible quantities are dropped; implausible ones are kept and flagged verify-now. Each rejection becomes a data-quality item.
  • Holds: HOLD-01 customer-requested delay (when live and F07 is set), split shipment pending, pre-order.

04

The engine contract

The runner calls evaluate(snapshots, cfg, as_of) -> EngineResult. It must be pure: no I/O, no clock, no database. A setting picks the in-repo engine or an external one.

Config is frozen and has no defaults: any missing key raises ConfigKeyError and fails the whole run. Any other error fails one order only.

Details: the switch, stub and check_runtime

How the engine is chosen (svc/engine/switch.py:18)

  • ENGINE_IMPL defaults to stub (svc/core/settings.py:24). Any value other than stub or real raises an error.
  • real imports orderflow_engine when called. If the package is missing it fails with "real engine not installed", and a result that is not an EngineResult is refused.

What stub.evaluate() does (svc/engine/stub.py:47)

  1. check_runtime (evaluate.py:98): for every rule that will run, its template is registered, its required params resolve, its custom function or anomaly check exists, and a hard stop has its acknowledgement and routing settings. The rule order must have no cycle. Any gap fails the run before anything is scored.
  2. Per order, evaluate_order: hard stops, rules, findings, combiner. A snapshot built for a different date is an error for that order.
  3. Errors. ConfigKeyError is re-raised and stops the run; anything else becomes an OrderError and the batch carries on.
  4. Ranks the priorities by warehouse and returns an EngineResult: engine impl and version, ruleset ID, config version and hash, date, findings, priorities, hard stops and errors.

Why it is built this way

  • Pure functions are what make golden cases, the dry-run preview and the stub-or-real swap possible.
  • A missing config key is a ruleset problem that affects every order, so it stops the run; a bad record is one order's problem, so it does not.
Reads

settings.ENGINE_IMPL: "stub" (default) or "real", which imports an external package, orderflow_engine, not in the repo.

05

Hard stops first

Every non-later hard-stop rule runs before scoring, without the cohort filter, tier gate or holds. Each outcome carries routing and an acknowledgement deadline from config. Hard stops are never scored.

EU retail has 4 hard-stop entries: 3 live, 1 later.

Details: the hard-stop path

What run_hard_stops() does (svc/engine/evaluate.py:262)

  1. Runs every hard-stop rule except later ones (hard_stop_drafts, :251), calling the template directly: no cohort filter, tier gate or hold check. The templates are stop_threshold and flag_value, and their drafts carry 0 points.
  2. Sets a disposition (stop_disposition, templates/base.py:301). Inside the look-back, by how old the signal was when it arrived: fresh is a hold, up to stop.late.verify_now_max_age_hours is verify_now, older is a review_task.
  3. Raises each event once. Keys raised in earlier runs or already in this run are skipped.
  4. Adds routing and a deadline from stop.routing.<id> and stop.ack_minutes.<id>.
  5. Second pass: a VERIFY outcome for each extreme quantity flagged by the snapshot builder.

Other pieces

  • The runner writes one obligation per order, rule and event key, and reports overdue ones without moving them.
  • In the combiner, any hard-stop outcome sets the action to hold_and_escalate and marks the priority as stopped. It never adds points.

Why they cannot be switched off

Two guards: ruleset validation refuses a hard stop whose status is not live (ruleset.py:301; later only if listed as a later hard stop), and the in-app config drafts refuse the same change (drafts.py:142). A suspected-fraud or export-restricted order must reach a person whatever the score, the tier or any hold says.

06a

Template rules

Rules run in dependency order (a floor or shares_with target first, otherwise file order). Each rule passes four gates: cohort, account tier, the template itself, then holds.

Off and later rules never run. Shadow rules run and record findings, but score 0 in the combiner.

Details: rule order, gates and templates

Rule order (svc/engine/evaluate.py:66)

  • Keeps rules that are not hard stops, not off or later, and not holds.
  • Runs a rule's dependencies first: rules named in its params or applies_to, and the target of shares_with. Otherwise file order. A cycle raises ConfigKeyError. The order is cached per ruleset, version and hash.

What run_rule() does (evaluate.py:214)

  1. Cohort. applies_to can test channel, region, basket value at or above / below, item category, another rule having fired, or any of these. Outside the cohort, the rule is skipped and nothing is stored.
  2. Tier. If the rule needs more data than the order's tier has, it is not assessed.
  3. Template. The registered function runs on the snapshot, the params and earlier outcomes.
  4. Holds, only if it fired. A hold whose scope matches the rule turns it into a stored not-applicable. Evidence that arrived after the hold was set is never held back.
  5. A fire with no drafts becomes Clear.

The template registry (templates/base.py:121)

  • Each template registers with @register: required and optional params, reason placeholders, the event-key families it supports, and whether it scores, is a hard stop or is a floor. A name registered twice is an error.
  • Ruleset validation uses the same registry to check each rule, so a rule cannot ask for params its template does not take.
  • custom dispatches on params.function to a second registry: split_shipment_ladder and hazmat_carrier_check.

Why templates

42 ruleset entries share 14 templates. Writing each rule as data on a tested template keeps the numbers in the ruleset, where operations reviews them, and leaves new code only for logic that genuinely does not fit.

06b

Anomaly checks

The order-level checks AN-P01 to AN-P05 run as rules through the stat template, mapped to the signal head. Four are shadow and AN-P05 is off.

Each flag records whether a live rule already scored the same event (counted_by_rule).

Details: the stat template

What the stat template does (svc/engine/templates/stat.py:44)

  1. Runs the check for the rule ID: run_check(snapshot, cfg, rule_id) looks it up in STAT_CHECKS (svc/engine/stats/), with settings from the ruleset's stats: section.
  2. Turns each flagged item into a draft at 0 points with a signal: event key.
  3. Marks overlap. If a live, non-signal rule already scored the same event for this order, the draft records counted_by_rule with the lowest such rule ID.
  4. No flags but some items clear gives Clear; only not-assessed items gives NotAssessed with the missing fields.

The five checks

AN-P01 basket far above the customer's usual, AN-P02 carrier transit time drifting, AN-P03 repeated address edits, AN-P04 slower than similar orders, AN-P05 return rate rising (off: no returns feed yet).

Things to know

  • The stats API calls the same run_check, so a chart on the order page always matches the stored finding.
  • AN-P04 needs a peer table, which the runner builds per batch (stage 02).

06c

Injected signals and ML

The snapshot can carry injected_findings from other engines (anomaly or ML signals). They are appended after the rule findings and go to the combiner as they are.

The dashed lane marks a path that exists in the contract but carries nothing in a normal run.

Details: injected findings

What happens to an injected finding

  1. Built in the snapshot by _injected (svc/engine/snapshot.py:490): a Finding in state fired, with the rule ID, kind, head, points, event key and reason given in the row. Status defaults to shadow.
  2. Appended after the rule findings in to_findings (evaluate.py:433), unchanged.
  3. Combined like any other finding. Shadow scores 0; a live one in the signal head would count, up to the tier's signal cap (Tier B 10, Tier A 0), and only the highest signal is kept.

Who fills it today

  • Test fixtures only: the rule test kit (casekit.py:203) and the golden files, such as AN-P02 at 3 points in shadow in worked example 1.
  • The runner's row loader never sets it, and no code feeds engine.prediction rows into it.

Why it exists

It is the contract's slot for findings from another engine, such as a delivery-delay model, without changing the rules path. Wiring it is a decision for the ML work, and it sits behind a review-only stage either way.

07

Outcomes become findings

The three lanes rejoin. Each fired draft becomes one Finding that records rule ID and version, head, points, event key, reason text and evidence row IDs. Not-assessed outcomes become 0-point findings that name the missing fields.

Details: to_findings

How each outcome is recorded (svc/engine/evaluate.py:381)

  • Fired: one fired finding per draft, with raw points, event key, reason, evidence, severity, days late and any floor band and action. Counted points stay 0 until the combiner fills them. The rule's head is marked assessed.
  • Clear: no row, but the head is marked assessed.
  • Not assessed: a 0-point row, reason "Not assessed: ...", listing the missing field IDs.
  • Not applicable, not a cohort miss (for example, held): a 0-point not_applicable row with the reason.
  • Cohort miss: nothing stored.

Injected findings are appended last. The set of assessed heads goes to the combiner for the coverage line ("delay, service, value assessed; signal shadow").

Things to know

  • A placeholder the draft does not supply renders as empty text rather than failing the run.
  • Event-key strings come only from keys.py helpers, so two rules that see the same shipment, ticket or stock reading produce the same key.

Why record misses and gaps

"Not assessed" is a data gap to close, never a sign that the order is fine. Storing it lets staff and the coverage line see what the score could not look at.

Reads

The outcome per rule ID, the rule entries, and the reason templates with their placeholders.

08

The combiner

A pure function from findings and hard stops to one Priority: separate shadow, count once by event key, keep one signal, cap each head and the total, band the score, apply floors, pick the action, write coverage.

Try it with the golden worked examples in the combiner playground below.

Details: combine() step by step

What combine() does (svc/engine/combiner.py:96)

  1. Tier picks the caps and bands.
  2. Separate. Only fired findings can score. Live floors are set aside (they never score); shadow floors are not applied. Shadow findings, or findings with no head, score 0.
  3. Count once by event key. Highest points wins; on a tie, the lowest rule ID. Losers are dropped_same_event.
  4. Signal slot. Only the highest signal finding is kept.
  5. Head caps, then the total cap. Within a head, findings fill the cap highest points first; a partial fit is counted at the reduced value, no room left is dropped_cap.
  6. Score band from the tier's cut-offs. Tier A has no Rush cut-off, so Rush comes only through a floor.
  7. Floors. The highest floor band raises the band if it is higher. It never adds points.
  8. Action. The band's action; a floor's own action if it is more intensive (action_intensity); the channel fallback if that action's channel is off; hold_and_escalate if there is any hard stop.
  9. Coverage line from the assessed heads.

Each step writes a trace line onto the priority, for example "count-once: LATE-R02 dropped, same event ship:SHP-1 as LATE-R01 (10 pts)".

Things to know

  • Holds are not applied here; they acted in stage 06a. Task-only holds pass through onto the priority.
  • The config's count_once, count_once_tie and signal: settings are not read; the behaviour is fixed in code, and validation only accepts the values that match it.

Why caps, then floors

Caps stop one area, such as many open support tickets, from crowding out everything else. Floors guarantee a minimum band for risky combinations, such as a missed promise date on a repeat-complaint account, without inflating the score that ranks orders.

combiner.* config: heads, kind_to_head, caps and bands per tier, actions, action_intensity, channels and fallbacks, tie-break.

09

Rank, write, and show

Priorities are ranked per warehouse by the ruleset's tie-break. Back in the runner, the result is written to engine.* tables, which feed the pick list and the Holds screen.

Details: ranking and the run's writes

Ranking (svc/engine/combiner.py:251 and :276)

  1. Priorities are grouped by warehouse.
  2. Each group is sorted by the ruleset's tie_break: band (highest first), score, days late, order age (oldest first), Tier B before Tier A, then order ID so the order is always the same.
  3. Ranks start at 1 within each warehouse.

What the runner writes (svc/engine/runner.py:361)

  • engine.finding: every finding with its final state and counted points.
  • engine.priority: one per scored order, with the tier's total cap.
  • engine.hard_stop_outcome and engine.hard_stop_obligation: an obligation is created once per order, rule and event key.
  • engine.data_quality_item: the rows the snapshot builder rejected, for scored orders.
  • engine.feature_snapshot: a feature vector per order (feature set fs-2026.11), refused if it holds any customer-identity field.
  • engine.run: orders scored and errored, hard stops, errors, status and finish time.

Why snapshots

The feature snapshots are a dated record of each order's features on each run, kept beside the result they produced. The identity guard refuses any identity field (names, emails, phone numbers, addresses) before a vector is stored.
